# Refuerzo de seguridad de la primera versión

Cambios locales del 15 de noviembre de 2026. Se mantienen los enlaces de correo, los cinco roles y los módulos de la V1. No equivale a una certificación de seguridad absoluta ni a una prueba contra un servidor público.

## Comportamiento que cambia

- Login: cinco solicitudes por minuto por identificador e IP y treinta por IP. El bloqueo de cuenta existente se conserva. Una clave incorrecta obtiene un mensaje genérico; los detalles de estado se muestran después de comprobar la clave.
- Recuperación y registro: cinco solicitudes por minuto por IP y diez por hora por dirección. La recuperación responde igual si la cuenta existe, no existe o ya solicitó un enlace reciente. El trabajo de recuperación se guarda cifrado y utiliza la cola existente. El tiempo mínimo de respuesta es 200 ms; esto reduce diferencias ordinarias, pero no garantiza tiempos idénticos ante congestión o fallas del servidor.
- Enlaces públicos: diez intentos por minuto por IP. Los nuevos tokens se guardan como SHA-256 de una credencial aleatoria de 60 caracteres. El valor guardado no sirve como enlace. Se conserva la caducidad y el formato de las URL.
- El consumo de enlaces y el restablecimiento de contraseña usan transacciones y bloqueos de fila. Un enlace no puede aplicarse dos veces de forma simultánea. Los enlaces comprueban el correo destinatario cuando esa información existe y el estado permitido de la cuenta.
- Las cuentas nuevas deben establecer su contraseña antes de acceder, incluso después de verificar el correo. La bandera interna no se acepta mediante asignación masiva ni se devuelve en el JSON del usuario. Las cuentas activas existentes conservan su acceso.
- Cambiar correo exige `current_password`: es la contraseña del actor que autoriza la operación, también cuando administra otra cuenta. El formulario web ya la solicita. Otros clientes, incluida una app móvil, deberán enviar este campo en esa operación.
- Contraseñas nuevas: al menos 8 caracteres y hasta 72 bytes (72 caracteres ASCII), con mayúscula, minúscula, número y símbolo. La verificación de claves antiguas al iniciar sesión conserva su funcionamiento. Se revocan sesiones y enlaces pendientes al cambiar contraseña, correo, rol, estado o asignaciones del usuario.
- Los tokens Bearer caducan a las 12 horas por defecto. La interfaz vuelve al acceso al recibir 401. `SANCTUM_EXPIRATION` permite ajustar el plazo; no usar cero como forma de desactivar la caducidad.
- Las consultas de disponibilidad de correo, cédula y nombre de usuario requieren autenticación y permiso para gestionar usuarios; sesenta consultas por minuto por usuario e IP.
- CORS permite el origen de `FRONTEND_URL` y los adicionales explícitos. CORS es una restricción del navegador; la autorización del backend sigue siendo obligatoria para cada operación.
- Logos de emisor, sucursal y carga independiente: raster admitido, extensión permitida, máximo 2 MB y 4096 × 4096 píxeles. Se decodifican y vuelven a codificar como PNG, con nombre UUID. Se elimina la alternativa que guardaba la extensión enviada por el cliente si fallaba el procesador. GD o Imagick deben estar instalados. Los archivos `.p12` no se trasladan al almacenamiento público.
- El backend añade cabeceras de seguridad y deshabilita respuestas de depuración en producción. Los errores internos 5xx se ocultan; el 501 de módulos pendientes conserva su explicación funcional.
- El frontend elimina el registro del token de recuperación, usa `no-referrer`, aplica CSP para bloquear scripts inline, externos y `eval`, y sólo adjunta el Bearer al origen configurado de la API. Los enlaces a nuevas pestañas utilizan `noopener,noreferrer`.

## Activación en el entorno habitual

La validación funcional se realizó sobre copias y bases de ensayo en `127.0.0.1:55435`, sin tráfico al SRI ni correos reales. El 15 de noviembre de 2026 también se aplicaron las tres migraciones pendientes en la base de desarrollo configurada, mediante `php artisan migrate --force --no-interaction`, tras generar y verificar un respaldo PostgreSQL fuera del repositorio. Se conservaron las 48 tablas existentes y sus datos; se verificaron las columnas originales y la conversión prevista de cada token. Se añadió la tabla `sri_tareas`, además de las columnas nuevas. Las instrucciones siguientes corresponden al despliegue en otros entornos y a los pasos de operación que deben mantenerse:

1. Revisar el diff y respaldar la base de datos y los archivos privados. Desplegar frontend y backend de forma coordinada.
2. Configurar `FRONTEND_URL` con la URL real de la web, `APP_URL` con la API y `CORS_ALLOWED_ORIGINS` sólo con los orígenes adicionales necesarios, incluido su puerto. Un origen no lleva ruta ni barra final. La API móvil nativa sin cabecera Origin no depende de CORS.
3. Ejecutar en el backend `php artisan migrate --force` para añadir `password_setup_required` y convertir los tokens anteriores a resúmenes. No ejecutar `migrate:fresh` en datos reales. Esta migración no cambia contraseñas ni activa o suspende usuarios.
4. Ejecutar `php artisan config:cache` después de configurar el entorno y `php artisan queue:restart` para que los trabajadores carguen el código nuevo. Mantener un trabajador de la cola predeterminada activo y supervisado; por ejemplo, `php artisan queue:work --tries=3 --timeout=120`. La recuperación ahora necesita este trabajador. Verificar `queue:failed` y probar la recepción real por SMTP.
5. Compilar la web con `REACT_APP_API_URL` apuntando a la API y `GENERATE_SOURCEMAP=false`. Servir el directorio `build` mediante el servidor web; no publicar `npm start` ni el servidor PHP de desarrollo en Internet.
6. Usar HTTPS en web y API, `APP_ENV=production`, `APP_DEBUG=false`, cookies seguras si se utiliza sesión web y permisos mínimos sobre archivos y base de datos. Publicar sólo el directorio `public` de Laravel. `.env`, certificados, respaldos, logs, `vendor` y código del backend no deben servirse como archivos públicos. Deshabilitar ejecución de PHP/scripts en cualquier directorio de cargas públicas.
7. Configurar la web estática con `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` y una CSP HTTP con `frame-ancestors 'none'`. La meta CSP incluida no puede imponer `frame-ancestors`. Activar HSTS cuando el dominio funcione completamente con HTTPS. Si hay proxy inverso, confiar sólo en los proxies reales y comprobar que Laravel reconoce HTTPS.
8. Hacer una prueba real de alta → verificación → establecimiento de contraseña → login, recuperación, cambio de correo, sesión expirada y POS. Los resultados locales no demuestran por sí solos la configuración del hosting o del correo público.

## Compatibilidad y límites que requieren seguimiento

- Los enlaces anteriores siguen usando su mismo valor original; la migración modifica su representación en la base. Los resúmenes son irreversibles: volver al código antiguo no puede recuperar texto de esos tokens. Una reversión requiere plan coordinado de código/base o invalidar y reenviar enlaces; no basta con `migrate:rollback`.
- Algunos tokens antiguos de establecimiento de contraseña carecen de destinatario en metadata. No se puede reconstruir con certeza el correo histórico. Si se sospecha de una exposición o cambio de correo anterior a este refuerzo, invalidar esos enlaces y usar una recuperación nueva por el correo actual verificado. No se presenta esa información histórica ausente como verificada.
- Se mantiene Bearer en `sessionStorage` para conservar la arquitectura actual. Una ejecución de JavaScript arbitrario dentro del origen podría acceder a esa sesión. CSP y el tratamiento seguro de contenido reducen el riesgo, pero no sustituyen la prevención de XSS ni una evaluación completa del despliegue.
- La CSP permite conexiones HTTP/HTTPS y WebSocket para conservar las configuraciones de desarrollo y API existentes. En producción conviene definir `connect-src` con la API y servicios exactos y retirar HTTP/WS. No se declara que esta política bloquee toda posible exfiltración.
- Los límites de aplicación no sustituyen un límite de conexiones/tamaño en el servidor web ni protección de red frente a DDoS. Usar almacenamiento de caché compartido si hay varias instancias.
- Auditoría de dependencias: Composer no reportó avisos conocidos en el archivo bloqueado. La auditoría inicial de npm reportó 39: 13 altas, 10 moderadas y 16 bajas, sin críticas. Una actualización compatible de Sucrase de 3.35.0 a 3.35.1 reduce el total a 36: 13 altas, 7 moderadas y 16 bajas. El árbol incluye herramientas de compilación y desarrollo dentro de `dependencies`, por lo que `--omit=dev` no las separa automáticamente del código que realmente se ejecuta en el navegador. No se aplicó `npm audit fix --force` ni una actualización mayor automática. Las alertas de React Router y la cadena heredada de Create React App requieren un trabajo separado de actualización y compatibilidad; un resultado de auditoría no demuestra por sí solo explotación en esta aplicación. La interfaz usa `createRoot` y `BrowserRouter`, no hidratación SSR. No se certifica ausencia de otras rutas de explotación.
- No se realizó pentest del servidor público, auditoría completa de infraestructura, recepción SMTP real ni nueva autorización externa ante el SRI. La configuración fiscal pendiente de la V1 no se resuelve mediante estas medidas de seguridad.

## Evidencia de validación

Las pruebas se conservan fuera de los repositorios, en el directorio temporal de auditoría `revision-v1-20261115-699628/seguridad-20261115`. No se agregaron tests al código que se preparará para commit.

Resultado: 180 pruebas de backend con 651 aserciones, 22 pruebas de frontend, 9 recorridos de V1 y 4 comprobaciones de seguridad en navegador aprobados; TypeScript y compilación de producción correctos. La compilación conserva advertencias de lint anteriores.

Se comprobaron regresión de V1, solicitudes malformadas, inyección SQL en acceso, límites, enumeración pública, contraseña temporal, contraseñas débiles, enlaces usados/vencidos/de otro correo, suspensión, cambio de correo con reautenticación, sesiones vencidas, respuestas de error, CORS, logos con extensión ejecutable/SVG/contenido añadido/dimensiones excesivas y XML con entidades. Además se ejercitó la cola real de base de datos con carga cifrada, el enlace resultante, el restablecimiento y la revocación, y la competencia de dos procesos por el mismo token. Las capturas del navegador evidencian los recorridos de V1 y el tratamiento de contenido malicioso como texto. Los avisos de lint previos no se presentan como corregidos.
